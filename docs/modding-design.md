# Modding: foundation and future design

Implemented: namespaced block registration, duplicate/invalid identifier
rejection, optional lookup for unknown names, and explicit failure on required
unknown content or invalid numeric IDs. Built-in content registers through the
same BlockRegistry API that future content loading can use. Block definitions now
include six runtime texture tile IDs; a zero/white tile preserves vertex tint for
untextured definitions. Tile IDs, like block IDs, are runtime references and must
eventually resolve from stable material names in external content. The current
atlas is generated by built-in C++ content code. No file-based mod loader runs.

Planned first level: declarative block/material/item definitions with mod IDs,
versions, dependency ordering and asset lookup. Content names resolve to compact
runtime IDs after registration. Persistent data stores stable names and schemas.

Planned second level: Lua, with controlled APIs and events for placement,
destruction, simulation ticks, generation and crafting. Scripting must not expose
Vulkan handles or raw engine ownership. A future dedicated server reuses the
same world/simulation layer without initializing a window or renderer.

Planned third level: trusted native extensions using an explicitly versioned C
ABI. ABI compatibility, dependencies and error handling need a separate design;
no native plugin loading is present in v0.1.

Composite blocks and multiblock definitions will eventually supply separate
render, collision and occupancy data. These remain sparse chunk-associated data,
not an ECS entity per static block. See [world data](world-format.md) for the
planned representation. Lua, EnTT and content file formats are intentionally
deferred until their milestones.
