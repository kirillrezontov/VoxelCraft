# Modding foundation — SDK 1.0

Milestone 3 adds four separate extension paths. Existing Lua/data packs still use
mod API 1. World/region format 1, player format 10, network protocol 4, and the
existing saved-mod envelope are unchanged. Native SDK ABI 1 is a separate version.
See [verification](native-modding-results.json) for executed checks and limits.

| Extension | Actual interface | Activation |
| --- | --- | --- |
| Resource pack | `ResourceCatalog`, `resource-pack.json`, namespaced bytes | Client `--resource-pack PATH` (repeatable); menu-only replacement through `ClientApplication::activateResourcePacks` |
| Data/Lua mod | Existing `mod.json`/`content.json`, optional bounded `init.lua` | `--mods-dir ROOT`; executable Lua is unnecessary for declarative content |
| Trusted native mod | Installed C header/function tables, platform DLL/SO | Explicit `--native-mods ROOT` on client or server, at session bootstrap |
| Core source module | `ChunkMesher` concept + `vc_client_modules` | Configure `VC_CORE_MESHER=greedy`, `culled`, or `example`; rebuild client consumers |

## Build and use the installed SDK

From a configured VoxelCraft build:

```sh
cmake --install build/debug --component ModSDK --prefix sdk-install
cmake -S sdk-install/share/VoxelCraftModSDK/examples/native_sample \
    -B build/native-sample -G Ninja -DCMAKE_BUILD_TYPE=Debug \
    -DCMAKE_PREFIX_PATH="$PWD/sdk-install"
cmake --build build/native-sample
./build/debug/bin/voxelcraft --no-settings --mods-dir examples/data_mods \
    --native-mods build/native-sample/pack/Debug \
    --resource-pack examples/resource_packs/amber
```

The SDK package is `VoxelCraftModSDK` version 1.0.0. The exported targets are
`VoxelCraft::mod_sdk` (C11-compatible header) and `VoxelCraft::mod_sdk_cpp` (C++23
convenience wrapper). Neither links engine implementation, Lua, SDL, or Vulkan.
The example also builds in-tree with `VC_BUILD_NATIVE_EXAMPLES=ON`. Multi-config
builds select `--config Debug`; their pack also lives under `pack/Debug`.
The C++ target applies GCC's `-fno-gnu-unique` for plugin-owned inline globals.

The sample registers a cyan light-emitting block, a raw material, a stone-to-beacon
recipe, a load notification and three commands. `/native_sample:ping` is available
to players. `/native_sample:stamp 0 60 0` requires administrator permission and a
resident, unoccupied cell. `/native_sample:retire` disables the ping/load callbacks
without unloading code. Enter commands through the actual console. The data-only
`signal` example adds an amber beacon, crystal and recipe without a Lua script.
The Amber resource pack changes the live legacy menu/inventory palette.

## C ABI contract

`sdk/include/voxelcraft/native_mod.h` is authoritative. Export exactly
`vc_mod_query_v1`, with `VC_MOD_EXPORT`/`VC_MOD_CALL` and C linkage. Query receives
the requested major, a borrowed `vc_mod_host*`, and a host-sized output
`vc_mod_api*`. Check sizes and major **before** reading/writing a table. Each v1
required prefix is its published `sizeof` at ABI 1.0; a later compatible minor may
append fields. A larger returned table/minor is accepted when its required v1
prefix and reserved fields are valid. There are no optional v1 features. Do not
write beyond the output capacity passed in `struct_size`.

Use fixed-width scalars, opaque `void*` state, length-delimited UTF-8 strings and
explicit function pointers. Call arrays/strings are borrowed through that call;
copy anything retained. The host copies registration descriptors. It never frees
plugin memory. `destroy` must release plugin state in its own library and is
required for non-null state. There are no cross-ABI STL types, allocators, C++
classes, exceptions or Vulkan objects. The C++ wrapper catches exceptions in its
entry/lifecycle thunks; plugin callbacks must contain their own exceptions.
A query that fails or returns an invalid table must clean up any state it created;
the host cannot safely invoke an incompatible destroy function.

Host operations return `vc_mod_status`. `last_error` is a borrowed diagnostic,
valid until the next host call on that module. All host operations and callbacks
run on the runtime's owning simulation thread. Wrong-thread calls are rejected
without mutating module state. Plugin-owned threads must not retain call-borrowed
data and must be joined by `stop`. The API provides no asynchronous host jobs.

Content registration is restricted to bootstrap and the owning namespace.
Block items are generated by the existing registry; ordinary items and recipes
are installed through the same gameplay services as built-in/data content.
World access is restricted to an active event/command, resident chunks, valid
content identifiers, bounded coordinates and player collision checks. Edits and
notifications are staged per invocation. A host failure invalidates the whole
invocation even if the plugin ignores its return value. Failed event callbacks
are disabled; failed commands report an error. This is rollback of host-mediated
effects, not a transaction around arbitrary native memory/filesystem activity.

## Discovery, dependencies and lifetime

`NativeModRuntime::discover` reads metadata without opening libraries. A pack is
a child of the explicit root and contains `native.json`:

```json
{"id":"native_sample","version":"1.0.0","abi":1,
 "library":{"linux":"native_sample.so","windows":"native_sample.dll"},
 "dependencies":{}}
```

Libraries must be local portable basenames with the selected platform suffix.
Canonical pack/library containment rejects traversal and escaping symlinks.
The complete dependency graph, exact versions, namespace conflicts and cycles are
checked before any DLL/SO is opened. Native packs may depend on native or already
loaded data packs; existing data/Lua dependency declarations cannot depend on a
native pack in this version. Library architecture must match the host. Loader
errors include missing entry points. Windows uses restricted `LoadLibraryExW`
search flags; Linux uses `RTLD_NOW | RTLD_LOCAL`.

Bootstrap stages a copy of content registries, negotiates/starts modules in
sorted dependency order, validates full item/recipe references, then publishes.
A failure stops/destroys started/valid modules and discards staged registrations.
At shutdown dispatch is disabled first; reverse-order `stop` and `destroy` run;
callback storage is cleared before libraries close in reverse order. Command
registry closures hold only weak host guards and tokens. They cannot call an
expired, stopped or retired native function. Shutdown requires the owner thread
outside dispatch. Module destruction belongs to session content lifetime.

This implementation offers session shutdown, not arbitrary hot unloading.
Native code runs with process privileges and is trusted; it is not sandboxed.
The plugin contract must quiesce its own jobs/references before returning from
`stop`. An OS loader may retain code mappings. Capability checks and the ABI
cannot prevent malicious native code from violating this contract.

Native identity/version and pre-existing opaque saved records use the original
saved-mod envelope. Missing-pack records survive save/reload. SDK 1.0 has no
mutable native state-serialization API, actor factory, UI widget, GPU-resource or
background-job API. Add these as versioned, owned capabilities when required;
do not expose game C++ objects across ABI 1. Native callbacks currently cover
load, tick, place, break and craft; commands reuse real server permission checks.

## Resource providers and budgets

`vc_resources` owns `ResourceCatalog`. `activate` validates a candidate set and
publishes it atomically with a revision. Providers sort by descending priority,
then lexical pack ID. Built-in assets are the fallback. Resource IDs use
`namespace:path/segments`; traversal, URLs, empty segments and nonportable names
are rejected. `load` returns owned bytes; `loadBuiltin` supports fallback after a
consumer detects a semantic error. `operator()` is a VoxelUI-compatible optional
byte-provider shape. It does not parse XML/SVG or execute code.

A pack contains `resource-pack.json` and `resources/<namespace>/<path>`:

```json
{"id":"amber","name":"Amber stone","version":"1.0.0","priority":100}
```

The actual legacy consumer is `voxelcraft:legacy-theme.json`. It validates the
existing Theme's four-channel colors, rejects unknown properties/nonfinite
values, and falls back to built-in/compiled colors on invalid replacement.
Application-owned catalogs outlive session users. Pack changes are rejected
while a session is active; later VoxelUI integration can add an owned reload flow.

| Boundary | Limit |
| --- | --- |
| Native manifest | 16 KiB, JSON depth 16, 1024 scanned root entries |
| Mods | 32 combined data/native; 32 exact dependencies per native pack |
| Native registrations | 128 blocks/items/recipe declarations per module; 128 aggregate installed recipes |
| Native callbacks | 64/module, nonzero owner tokens below 4096 |
| Invocation | 64 unique edits, 16 notifications; event dispatch aggregate 4096 edits/256 notifications |
| Resource packs | 32 providers; priority -1000..1000; 16 KiB manifest/depth 16 |
| Resource bytes | 16 MiB maximum/request; consumers can request a smaller bound |
| Legacy theme | 16 KiB, depth 4, finite RGBA channels 0..1 |
| Diagnostics | 1024 native bootstrap entries; 128 resource load failures |

Canonical checks prevent static traversal/symlink escapes. They do not isolate
concurrent hostile mutation of a writable directory; use trusted immutable native
roots and owned resource directories. Native executable code has no time/memory
sandbox. Existing Lua budgets remain separate. Raw material items without custom
icons use the game's existing missing-icon fallback.

## Core example

`examples/core_modules/warm_reference_mesher.hpp` satisfies `ChunkMesher`, delegates
the existing culled geometry and applies a warm vertex-color factor. Select with
`-DVC_CORE_MESHER=example`; rebuild `voxelcraft`. The same synchronous/background
queues and central gameplay algorithms consume the selected concrete type.
`CoreSelection.example` verifies real geometry/color output, and the Vulkan smoke
test executes that client in-world. It intentionally trades greedy geometry for
visible reference geometry; it is an example, not a performance recommendation.
